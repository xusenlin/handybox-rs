# HandyBox

<img src="assets/app-icon.png" alt="HandyBox 吉祥物" width="88" height="88">

[English](README.md) | 简体中文

一个使用 Rust 和 Slint 构建的、快速且离线优先的桌面工具箱。

HandyBox 把日常小工具集中到一个原生桌面工作区里。当前版本提供**中英文界面**、一个可用的**文档转 Markdown 工具**、一个支持 jq 查询的**JSON 工作台**、一个基于 sha2 与 age 的**哈希与加密**工具、一个基于 similar 的**文本对比**工具、一个基于 rxing 的**条码识别**工具、一个基于 clipboard-rs 的**剪贴板工作区**、一个可用的**磁盘清理**工具、一个可用的**图像处理**工具，以及最后一个工具的可导航、带说明的占位页面。无需账号、API Key、服务器、WebView，也不会上传任何文档。

用侧边栏底部的 **English / 中文** 可以立即切换语言。当前工具、搜索内容和已转换的文档都会保留。工具搜索同时支持两种语言和引擎名称。默认英文；选择会保存在本地，下次启动时沿用。

## 运行

先用 rustup 安装 Rust，然后在本仓库中运行：

```sh
cargo run --locked

# 启动时直接打开一个文档
cargo run --locked -- examples/sample.rtf

# 图片会在条码识别里打开
cargo run --locked -- examples/sample-codes.png

# 文件夹会在磁盘清理里打开并开始扫描
cargo run --locked -- ~/Downloads

# 传入两个路径即为一次对比：它们会在文本对比里并排打开
cargo run --locked -- old.txt new.txt

# 强制使用 CPU 渲染器做兼容性测试
SLINT_BACKEND=winit-software cargo run --locked

# 优化后的可执行文件：target/release/handybox
cargo build --release --locked
```

仓库锁定了 **Rust 1.88.0**、**Slint 1.13.1**、**anydoc 0.2.4**、**jaq 3** 系列 crate、**age 0.12**、**similar 3**、**rxing 0.9**、**clipboard-rs 0.3**、**trash 5** 和 **oxipng 10**；更新依赖时请一并提交 `Cargo.lock`。rustup 会在需要时自动安装锁定的工具链。首次下载依赖需要联网；构建完成后的应用完全在本地处理文档。

macOS 上需安装 Xcode Command Line Tools。Windows 上请使用 MSVC Rust 工具链和 Visual Studio C++ Build Tools。Debian/Ubuntu 上请安装桌面构建依赖：

```sh
sudo apt-get install build-essential pkg-config libx11-dev libx11-xcb-dev \
  libxcb1-dev libxkbcommon-dev libxkbcommon-x11-dev libgl1-mesa-dev \
  libfontconfig1-dev libwayland-dev
```

Linux 目前使用 X11（在 Wayland 会话中则走 XWayland）。原生文件选择器依赖 `xdg-desktop-portal` 以及对应桌面环境的 portal 后端。即便使用 CPU 渲染，也仍然需要图形桌面会话。

## 发布构建

常用命令都封装在 [Task](https://taskfile.dev) 里，`task --list` 可以列出全部：

```sh
task run                        # cargo run --locked
task run -- examples/sample.rtf # 启动时打开文档
task check                      # 格式检查 + clippy
task test                       # 工作区测试

task build                      # 三个平台，产物进 dist/
task build:native               # 只构建当前系统
task build:cross                # 只构建 Windows 和 Linux
```

`task build` 会在 `dist/` 下生成带版本号的优化压缩包，以及一份 `SHA256SUMS` 校验清单。三个平台统一发 zip：下载体积大约减半，也省得一个平台是压缩包、另外两个是裸文件：

```text
dist/handybox-0.1.0-macos-arm64.zip    # HandyBox.app
dist/handybox-0.1.0-windows-x64.zip    # handybox-0.1.0-windows-x64.exe
dist/handybox-0.1.0-linux-x64.zip      # handybox-0.1.0-linux-x64
```

版本号来自 `Cargo.toml` 的 `[workspace.package]`，不会在第二个地方重复书写。构建前会先清掉旧产物，`dist/` 里不会新旧版本混在一起。`dist/` 不纳入版本管理。

release 配置用构建时间换体积：`lto = "fat"`、`codegen-units = 1`、`strip = true`。fat LTO 冷构建要多花几分钟，换来约 8% 的可执行文件体积。`panic = "abort"` 还能再省一兆多的展开表，但刻意没有开启：工作线程依赖 `catch_unwind` 兜住畸形文档触发的解析器 panic，abort 会让整个应用直接退出。

macOS 发布的是 `HandyBox.app`，由 [`scripts/macos-bundle.sh`](scripts/macos-bundle.sh) 打包。裸的 Mach-O 可执行文件在 Finder 里双击会拉起 Terminal，也挂不上图标；只有 .app 才是正常的应用启动方式。脚本会写入 `Info.plist`，用 `sips`/`iconutil` 生成 `AppIcon.icns`，并用 `ditto` 压缩以保住 bundle 的可执行位和符号链接。打包在 `target/` 下进行，因此 `dist/` 里永远只有可发布的压缩包。Windows 和 Linux 的可执行文件由 [`scripts/zip-binary.sh`](scripts/zip-binary.sh) 压缩；Info-ZIP 会记录 Unix 权限位，Linux 二进制解压后依然可执行。Windows 本身就链接为 GUI 子系统程序，`.exe` 不会弹控制台窗口。

Windows 和 Linux 的二进制在 [`scripts/Dockerfile.cross`](scripts/Dockerfile.cross) 定义的纯构建容器里交叉编译，容器提供 mingw-w64 和 GNU 交叉链接器，以及 winit 后端需要链接的 Linux 桌面开发库。容器里的任何东西都不会打包进应用。宿主构建和交叉构建使用各自独立的 Cargo 缓存，不会互相覆盖产物。需要 Docker 正在运行。镜像的 tag 取自 Dockerfile 的内容哈希，改动工具链会自动触发重建，不会悄悄沿用旧镜像。

`task build` 需要在 macOS 上执行，因为 Apple 目标无法在容器里交叉编译。其他系统请分别使用 `task build:native` 和 `task build:cross`。

产物最多只有 ad-hoc 签名：没有 Developer ID 签名，也未做公证，因此首次启动时 macOS Gatekeeper 和 Windows SmartScreen 会给出提示。macOS 压缩包请用 Finder 或 `ditto -x -k` 解压；用命令行 `unzip` 会把系统给 bundle 附加的 `._` 伴生文件一并解出来，导致 `codesign` 报告封存资源缺失。

## 工具与实现状态

| 工具 | 引擎 | 当前状态 |
| --- | --- | --- |
| 文档转换 | `anydoc` | 已实现：选择/拖入文件、转换、查看 Markdown 源码、全部复制、导出 `.md` |
| JSON 工作台 | `jaq` | 已实现：校验、格式化、压缩、jq 语法查询、复制与导出 `.json` |
| 哈希与加密 | `sha2` + `age` | 已实现：SHA-256/SHA-512 摘要与校验、用密码或密钥进行 age 加密与解密 |
| 文本对比 | `similar` | 已实现：两段文本或两个文件的实时逐行对比、变更统计、复制与导出 unified diff |
| 图像处理 | `image` + `fast_image_resize` + `oxipng` + `nom-exif` | 已实现：列出文件夹中的图片、查看图片与 EXIF、缩放、PNG/JPEG/TIFF/BMP 互转、PNG 无损优化与批量导出 |
| 压缩与解压 | `zip` + `sevenz-rust2` | 占位：压缩包预览、创建与解压 |
| 条码识别 | `rxing` | 已实现：识别图片中的每一个二维码与条形码、标出各自位置、单条或整体复制 |
| 磁盘清理 | `sha2` + `trash` | 已实现：扫描文件夹中的重复文件、空文件与最大的文件，勾选、确认，然后移入系统回收站 |
| 剪贴板 | `clipboard-rs` | 已实现：收下复制过的文本、图片与文件引用，可选开启自动收集，随时放回剪贴板，图片还可另存为 `.png` |

计划中的引擎只记录在工具目录中，不会伪装成可用操作，也不会提前拉进生产依赖。`zip` 同时是开发依赖，用于构造真实的 DOCX 测试样本；`rxing` 的条码**生成**部分同样只是开发依赖——条码测试先画出码，再读回来。磁盘清理原定的引擎是 czkawka，最终没有采用；表中写的是它实际用到的东西，[下面的章节](#磁盘清理)解释了原因。条码识别用 `image` crate 解码图片，剪贴板工作区用同一个 crate 编码收下的图片，Slint 自身也带有图像相关的依赖，这些都不代表图像处理已经实现。

## 文档转换

1. 点击 **选择文件**、把一个文件拖到窗口上，或在启动时传入文件路径。
2. 转换会在后台工作线程中自动开始。源文件不会被修改。
3. 阅读生成的 Markdown 源码。**复制全文** 复制完整结果，**导出 .md** 会打开原生保存对话框。

转换器支持 anydoc 提供的格式：Word（`doc`、`docx`、`docm`）、PowerPoint（`ppt`、`pps`、`pot`、`pptx`、`pptm`、`ppsx`、`ppsm`）、Excel（`xls`、`xlsx`、`xlsm`、`xlsb`）、OpenDocument（`odt`、`ods`、`odp`）、PDF、EPUB、RTF 和 CSV。内容检测优先于文件扩展名；没有特征签名的 CSV 则按扩展名判断。

行为与当前限制：

- 单文件处理，**输入上限 64 MiB**，即使文件在读取过程中增大也会有界读取。一次拖入多个文件时，只会处理空闲状态下接受的第一个；没有批量队列。
- 支持文本型 PDF。扫描件/纯图片 PDF 页面会明确提示需要 OCR；本项目不包含 OCR。加密或损坏的文档会报告转换错误。
- Markdown 以**源码**形式展示，不做渲染。预览最多 **200,000 个 Unicode 字符**；复制和导出始终使用完整结果。视图按行渲染并做了虚拟化，只对屏幕上的那几行排版；代价是文字不可选中。需要取出内容请用**复制全文**或**导出 .md**。
- 切换工具时结果保留在内存中。不会自动保存转换历史。选择新文件后，在处理开始时清除旧结果；取消文件选择器则保留原结果。
- 导出会先在目标目录写入临时文件，再原子地落盘。是否覆盖由原生对话框负责确认。导出会拒绝覆盖输入文件，并要求 `.md` 扩展名。确认之后不会悄悄改变目标路径。
- 仅导出 Markdown，不会打包提取出的图片资源，也不保证还原源文档的视觉排版。复杂排版的效果取决于 anydoc 的提取质量。
- 同一时间只运行一个操作。工作期间仍可导航，但解析目前无法取消。输入大小上限并不等于对解压后数据或解析器峰值内存的硬限制；anydoc 有自己的解析器限制。未来可以用独立的工作进程为大负载加上硬性的内存/时间限制和取消能力。

可以试试仓库自带的小文件：[`examples/`](examples/)。

## JSON 工作台

1. 在**输入**里粘贴 JSON，或点击**打开文件**，也可以载入内置的**示例**。
2. 停下打字后会自动校验：编辑器下面那行会说明文档里有什么，或者第一个语法错误在哪一行哪一列。
3. 写好 **jq 表达式**后点**运行**（或按回车）得到缩进结果，点**压缩**得到紧凑结果。留空表达式就是 jq 的恒等式，因此不填即为格式化整份文档。
4. **复制全文**复制完整结果，**导出 .json** 会打开原生保存对话框。

校验结果显示在两张卡片下方，整行贯通，右侧是**严格（单个值）**开关。它决定什么算一份文档：关闭（默认）时像 jq 一样把多个顶层值读成 JSON 数据流；打开后，出现第二个值即报错。

引擎是 [jaq](https://github.com/01mf02/jaq)——jq 语言的 Rust 实现，标准库可用，包括 `map`、`select`、`group_by`、`@base64`、正则和日期函数。没有模块搜索路径，因此表达式无法访问文件系统或网络。

行为与当前限制：

- **单份文档最大 4 MiB。** 编辑器是一个整体排版的文本项，所以这个上限既是解析预算也是渲染预算。打开文件同样受此限制，非 UTF-8 文件会被拒绝。
- 文档只解析一次，进入 jaq 自己的值模型：校验、格式化和查询三者对文档的理解始终一致，超出 `f64` 表示范围的整数也不会丢精度。
- 与 jq 一样接受多个顶层值：JSON 流或 JSON Lines 文件会逐个值应用表达式。严格来说多个顶层值并不是一份 JSON 文档，所以状态行会写成「JSON 数据流」并给出值的个数，而不是报告单份文档有效。该行右侧的**严格（单个值）**开关会把这种输入直接判为错误，也就是 RFC 8259 对 JSON 文档的定义。该开关同时作用于校验和运行，不跨会话保存。
- 语法错误会给出**行号与列号**；jq 的错误分成「表达式无法理解」和「表达式在该输入上中止」两类，两者都在**技术详情**标签下保留引擎自己的原文。
- 单次运行在**输出 20000 条或运行 5 秒**后停止并说明原因，因此 `repeat(.)` 这类无穷表达式会返回可用的前缀，而不是一直占着工作线程。只循环不输出的表达式无法中断；`halt` 只结束本次运行，不会结束应用。
- 结果视图与转换器一样做了虚拟化，同样有 **200,000 字符**的预览上限；复制和导出始终使用完整结果。
- 导出会先写临时文件再原子落盘，要求 `.json` 扩展名，并拒绝覆盖打开的那份文档。是否覆盖由原生对话框负责确认。
- 切换工具时输入与结果都保留在内存中。除非导出，否则不会写入磁盘。

可以用 [`examples/sample.json`](examples/sample.json) 试试 `.tools | map(.key)` 或 `.tools[] | select(.ready) | .engine`。

## 哈希与加密

三种操作共用同一个源文件：任何文件都可以计算摘要、加密或解密，顶部的切换只决定在它旁边问什么。点击选择文件、在本页时把文件拖到窗口上，或在启动时传入路径。`.age` 文件无论当前在哪一页，都会在这里以 **解密** 打开。

**校验和** 只读一次文件，同时给出 SHA-256 和 SHA-512。把校验和粘进输入框即可比对：长度就说明了算法，不需要再选；直接粘贴一整行 `shasum` 输出也可以，因为只读第一个字段。结论是结果下方的一行绿字或红字——不一致会直接说出来，而不是留给你逐位去比。

**加密** 与 **解密** 使用 [age](https://github.com/str4d/rage) 的两种模式：

- **密码**（scrypt）。工作因子按本机速度取约一秒，加密和解密各一次。没有找回途径：密码丢失就等于文件丢失，所以在确认之前可以用 **显示** 把输入框取消遮蔽。
- **公钥**（X25519）。粘贴一个或多个 `age1…` 接收者，每行一个或用空格分隔；**生成密钥对** 会新建一对，并把公钥追加到输入框。私钥只在结果面板显示这一次，不会写到任何地方——请自行保存，否则加密给该公钥的文件将再也打不开。解密时使用对应的 `AGE-SECRET-KEY-1…`。

行为与当前限制：

- **单个文件最大 2 GiB。** 全程按固定分块流式处理，不会整份读进内存，所以这个上限是耐心预算：工作线程一旦开始就无法中断。
- 文件头已经说明它需要哪种密钥，因此用密钥去开密码保护的文件（或反过来）会被如实指出，而不是丢出 age 笼统的“没有匹配的密钥”。
- 输出先写临时文件再原子落盘。加密结果必须使用 `.age` 扩展名，两个方向都不会覆盖正在读取的文件。是否覆盖由原生对话框确认。
- 接收者和密钥在读写任何内容之前就会解析，因此写错只会得到一条提示，不会产生残留文件。
- 密钥只存在于页面输入框和工作线程的命令中。除了你选定保存位置的那个文件，不会写入磁盘。

## 文本对比

1. 在**原始**和**修改后**里粘贴或输入文本，点击任意一侧的**打开文件**，也可以在本页时把文件拖到窗口上——它会填进还空着的一侧，两侧都有内容时则替换「修改后」。
2. 停止输入后，对比会自己运行。这里没有「开始对比」按钮，因为没有什么需要你去要求。
3. 结果逐行显示：每一行带着它在自己那一侧的行号、`+` 或 `-` 标记，以及一层底色。
4. **复制 diff** 和 **导出 .diff** 产出标准的 unified diff，上下各带三行上下文。

两个开关决定什么算作改动，改动后都会立即重新对比。**忽略空白差异** 会把仅有空格差别的两行视为同一行——缩进和行尾空格通常不是任何人要找的改动。**只看变更** 会略去没有改动的整段，并用一行说明省略了多少行。**对调两侧** 换个方向读同一次对比，每一侧的文件也跟着一起换。

面板下方的一行统计新增和删除的行数、改动的处数，以及两侧的相似度。完全一致时会用绿字说明，此时也没有 diff 可以复制或导出。

行为与当前限制：

- **每侧最多 2 MiB。** 每一侧都是一个装着整段文本的编辑器，所以这个上限既是解析预算，也是渲染预算。读取文件用同样的上限，非 UTF-8 文件会被拒绝。
- 对比是**按行**进行的。比较前会去掉行尾换行符，因此同一份内容在 Windows 和 Unix 上写出来是一致的，而不是每一行都算改动。行内的差异不会高亮：Slint 1.13 没有富文本，高亮没有地方可放。
- Myers 算法最坏情况下是平方复杂度，因此 **5 秒**后会停止继续优化并说明；此时给出的仍是正确的差异，只是不是最小的那一份。面板最多显示 **20000 行**，复制和导出始终使用完整结果。
- 对比的是屏幕上的两段文本，而不是磁盘上的文件：打开文件后再编辑，比较的就是你编辑之后的内容。记住文件只是为了在 diff 头部写出它的名字、给导出建议一个文件名，以及拒绝覆盖它。
- 导出先写临时文件再原子落盘，必须使用 `.diff` 或 `.patch` 扩展名，并且拒绝覆盖参与对比的任何一个文件。是否覆盖由原生对话框确认。
- 切换工具时两段文本都保留在内存中。除非你主动导出，否则不会写入磁盘。

## 条码识别

1. 点击**选择图片**、把图片拖到窗口上，或在启动时传入一张图片。不管当前在哪个页面，图片都会在这里打开——扩展名已经足够判断它是什么。
2. 识别会自己开始。条码没有什么需要配置的，所以也没有「开始识别」按钮。
3. 左侧显示图片，识别到的每个码都被框出并编号；右侧按阅读顺序列出它们的内容。点击任意一行或任意一个框，两边都会高亮同一个码。
4. **复制**取走单个码的内容，**复制全文**把每个码各占一行一起取走。

引擎是 [rxing](https://github.com/rxing-core/rxing)，ZXing 的 Rust 移植。支持二维码、Micro QR、Data Matrix、Aztec、PDF417、MaxiCode，以及常见的一维码（EAN-8/13、UPC-A/E、Code 39、Code 93、Code 128、Codabar、ITF、GS1 DataBar）。图片通过 `image` crate 读取：PNG、JPEG、GIF、BMP、WebP、TIFF、ICO、TGA、QOI 与 PNM 系列。

行为与当前限制：

- **单张图片最大 32 MiB、4000 万像素。** 识别要在整张图上来回走好几遍，因此像素数才是真正的预算——很小的文件也可能解码出极大的图像，所以先读图片头，再决定要不要分配内存。
- 图片里没有码是一个**答案，而不是错误**：状态行会这样说明，图片也继续留在页面上。这个工具会报的错误都与文件本身有关——找不到、读不了、不是图片。
- 识别默认开启 try-harder，并且会同时尝试浅色印在深色上的码。多码识别一无所获时，还会用缩放和滤波再试一次，这一步正是照片里那个唯一的码能被读出来的原因。但模糊、残缺或太小的码依然读不出来。
- 位置以**图片的比例**表示，因此预览无论画多大，框都落在同一个地方。一维码是以一条横穿条纹的线定位的，框可能是扁的；每个标记都有最小尺寸，并始终以码的中心对齐。
- 预览就是识别所用的那张图，最长边缩到 **900px** 后作为像素交给页面。图片文件只在工作线程上打开一次，事件循环不会再去读它。
- 识别出的文本用界面字体而不是等宽字体显示：二维码里写中文是再常见不过的情况，而等宽字体没有对应的字形。
- 切换工具时结果保留在内存中。这个工具只读取，不会写入磁盘。

可以试试 [`examples/sample-codes.png`](examples/sample-codes.png)：同一张图里放了一个二维码、一个 Code 128 和一个 EAN-13。

## 剪贴板

1. 点击**读取剪贴板**，把此刻剪贴板里的内容收下来：一段文本、一张图片，或者文件管理器复制的文件。
2. 打开**自动收集**后，之后复制的内容都会自动留在这里，不再需要点按钮。关掉它不会影响已经收下的内容。
3. 选中一条内容就能看到它的全貌——完整文本、文件引用对应的路径，或者图片本身。
4. **复制**把这条内容放回系统剪贴板，随时可以粘贴。图片还多一个**导出 .png**：图片是唯一没法只靠剪贴板离开的那一类——粘贴它需要一个收图片的地方，而文本和路径到哪儿都能粘。
5. **移除**丢掉其中一条，**清空**清掉整个工作区；两者都不会动系统剪贴板。

行为与当前限制：

- **只保存在内存中。** 不写磁盘，没有历史文件，关闭窗口即清空。和其他工具的结果一样，切换工具时内容会保留。
- **自动收集默认关闭。** 剪贴板里装密码和银行卡号的次数，和装一段文字一样多，所以在开关打开之前不会有任何监听，而打开这个开关是唯一的启动方式。
- 监听跑在自己的线程上，因为各平台对「剪贴板变化」的定义并不一致：Windows 和 X11 上是事件，macOS 上是需要轮询的 `changeCount`。那个线程只负责说*发生了变化*，随后的读取仍然是工作线程上的一个普通任务，和别的任务排在一起。
- 同一份内容复制两次只算**一条**，它会回到列表最前，而不是再留一份——包括你把某条内容放回剪贴板后，工作区自己又看到的那一次。
- **最多 60 条，单条文本 4 MiB，单张图片 32 MiB，总计 128 MiB。** 放不下时最旧的先离开；刚收下的那一条永远留下，哪怕它自己就超过了整个预算。
- 图片以 **PNG** 保存——这也是放回剪贴板时用的那一份——另外保留一张最长边不超过 480px 的缩略图供面板绘制。每条内容旁边写的是它自身的大小；缩略图占用的内存计入预算，但不属于内容本身，因此列表下方的合计正好等于各行之和。
- **导出 .png** 写出的是收下的那份 PNG，而不是旁边画的预览图；写入先落到目标目录下的临时文件，再原子地替换过去。路径没有 `.png` 扩展名时直接拒绝，而不是悄悄改掉——系统对话框已经就这个路径问过是否覆盖了。
- 文件引用会从平台给出的任意形式解码出来——有的系统给 `file://` URI，有的直接给路径，中间还可能带百分号转义。放回剪贴板的同样是文件引用，因此在文件管理器里粘贴得到的是文件本身。
- 富文本和 HTML 按随附的纯文本收下。如果剪贴板里只有工作区无法保存的格式，手动读取会明确提示，自动收集则直接跳过——毕竟那次读取并不是谁要求的。
- 面板最多排布一条文本的 **200000 个字符**，和这里其他预览一样；放回剪贴板时用的始终是完整内容。文本用界面字体而不是等宽字体显示，因为别人复制的东西是中文句子的概率和是命令一样高；路径仍然用等宽字体，这样更容易对齐。

## 图像处理

1. 点击**选择文件夹**、把文件夹拖到窗口上，或者直接拖一张图片进来——单张图片会按它所在的文件夹打开，并把它显示出来，因为从四十张照片里拖出一张，本来就是这个意思。
2. 文件夹里的图片列在左边。**点击某一行**就能查看它：右侧用同一张卡片显示图片及其尺寸、格式、颜色，下面接着相机留下的信息——是一张照片和它的说明，而不是两块面板。**勾选某一行**表示导出时要处理它。这两件事是分开的，所以你可以一路翻看，而不会改变自己即将写出的东西。
3. 选择输出格式，需要的话再填一个宽度，高度会自动跟随。JPEG 可以选质量，PNG 可以开无损优化。
4. **导出勾选…**先问你导出到哪个文件夹，确认之后才真正开始：在对话框里取消，页面保持原样，不会进入处理中状态。选定文件夹后，它用同样的设置逐张写出所有勾选的图片并显示进度；**停止**可以在两张图片之间结束它。批量结束后，全局浮层会停留更长时间，并显示请求、成功、跳过和失败的文件数，以及转换前后的总体积。

行为与当前限制：

- **永远不会覆盖任何文件。** 批量处理没有人可以问，所以目标文件夹里已有同名文件时会跳过并计数；被读取的那张图片也永远不会被写回去。因此导出到原文件夹这件事，在格式不同时没问题，在格式相同时就是什么都不做。
- 只读取所选的这一层文件夹，不会进入其中的子文件夹：批量处理应该只作用于人能在列表里看见的东西。
- **单次最多列出 1000 张图片**，**单张图片最大 64 MiB、5000 万像素**。列出只读图片头，所以五百张照片的文件夹也是毫秒级；而处理一张图片意味着把它整个展开，这正是单张上限存在的原因。
- 批量处理**一次只读、只生成、只写一张**，所以无论文件夹多大，内存都是平的，也因此可以在两张之间停下来。
- 可读取 PNG、JPEG、GIF、WebP、TIFF、BMP、ICO、TGA、QOI 与 PNM；**可写出 PNG、JPEG、TIFF 与 BMP**。输出里没有 WebP，是因为纯 Rust 的编码器并不存在：这个版本能读它，写不了它。
- **导出的图片不含任何 EXIF**——没有相机型号、序列号，也没有拍摄位置，编码器只写像素。原图带了什么就列在下方，因为准备把照片发出去的人应该知道里面有什么。
- 横着拍的照片在打开时就被摆正，因此缩略图、缩放结果和导出的文件都与相机当时显示的一致。
- 缩放保持比例，所以只需要选一个宽度。过程走 RGBA 和高质量滤波；PNG 输出时优化器会把灰度或索引色的图片还原回去，所以这段绕路在看得见的地方并不花钱。
- PNG 优化使用 **level 2**，而且只有在确实更小的时候才采用。优化器自带的默认档会为了几个百分点去尝试多得多的滤波与压缩组合，而这一步是有人在等着的。
- 当前查看的图片只解码一次，用于预览和读取元数据。批量导出会依次读取、处理并写出每一张已勾选的图片。
- 两个工具吃图片，两个工具吃文件夹，所以由你停在哪一页决定：停在这一页时拖进来的图片或文件夹归这里，否则分别归条码识别和磁盘清理。

## 磁盘清理

1. 点击**选择文件夹**、把文件夹拖到窗口上，或在启动时传入一个路径。扫描会自己开始——对这个工具来说，选一个文件夹就是在问「里面有什么」。
2. 选择要找的东西：**重复文件**、**空文件与空目录**或**大文件**。切换会用新的问题重新读一遍文件夹：结果属于它当时所用的那种模式，所以旧结果会被丢弃，而不是换个标签继续显示。磁盘上的内容变了之后，可以用**重新扫描**再读一次。
3. 勾选可以移走的内容。**每组只留一份**会勾上每组中除第一份以外的所有副本；**全选**用于空文件与空目录。大文件下不提供这两个按钮：它们只是大，并不是垃圾，哪些可以走只有人能判断。
4. **移到回收站…**会把列表下面那一行变成一句话，说清楚将要移走什么、移到哪里。**确认移动**执行这句话，**取消**则什么都不动。

行为与当前限制：

- **不会 unlink 任何文件。** 要走的内容一律进入系统自己的回收站——macOS 的废纸篓、Windows 的回收站、Linux 上的 freedesktop trash——点错了可以在大家本来就会去找的地方还原。整批选中的内容在**一次操作**里移走：撤销是一步，废纸篓的提示音也只响一次，而不是每个文件响一次。
- 重复**只按内容判断**：先按大小分组，再比较前 64 KiB 的 SHA-256，只有仍然相同的才整份读完比对。文件名、目录和时间戳对它没有任何意义；读不了的文件会被排除，而不是和它没能匹配上的文件归成一组。
- **每一组重复都必须留下一份。** 把某一组的所有副本都选中会被拒绝并给出提示：一个用来删掉多余副本的工具，不能成为删掉最后一份的那个。
- 每个路径在进回收站之前都会再检查一次——是否仍在本次扫描的文件夹内、是否仍是真实文件而不是链接、大小是否仍与扫描时一致、空目录是否仍然为空。期间发生变化的会被跳过并计入提示，而不是按旧结论删掉。
- **永远不跟随、不比较、也不删除符号链接。** 链接不是它所指内容的副本，而指回上层目录的链接会让遍历永远走不完。
- 跳过版本库与系统目录：`.git`、`.hg`、`.svn`、`.Trash`、`.Spotlight-V100`、`.fseventsd`、`$RECYCLE.BIN` 和 `System Volume Information`。仓库里的副本是有意为之的。
- **单次扫描最多 20 万个文件、读取 16 GiB、运行 60 秒**，最深 64 层。达到上限时会交出已经找到的内容，并明确说明这只是部分结果，而不是假装扫完了；比对从最大的文件开始，所以即使预算用尽，也花在了真正占地方的地方。大文件视图最多列出 100 个。
- 空目录只在整棵树的最上层报告一次：移走它就带走了下面的一切，逐层列出只会让同一个目录被要求删除三次。
- 默认不勾选任何内容，切换语言也不会丢失已有的勾选。删除之后，结果里去掉的正是进了回收站的那些路径，不必重新扫描整个文件夹；只剩一份的组自然不再是「重复」。
- 扫描可以**被新的问题打断**：扫描期间切换模式会举起一个标志，扫描在每个文件之间、以及正在计算哈希的每一个数据块之间读取它，因此新问题的答案在一个数据块之后就开始，而不是等整个文件夹读完。模式切换按钮在扫描期间保持可用正是为此；页面上的其他操作仍和别的工具一样要等这次操作结束。结果保存在内存中，不会写入磁盘。
- **czkawka 原本是计划中的引擎，最终没有采用。** 它的当前版本要求 Rust 1.92 / 1.94，而本仓库锁定 1.88；能构建的那个版本会带进一整套音频、视频与 RAW 图像依赖——大约五十个 crate，还自带 logger、本地化和缓存文件——而这里需要的三种扫描只有几百行 `tools/cleanup.rs`。那棵依赖树里真正值得要的是相似图片检测，这一版没有做。

```text
Slint 组件 → 回调 → 控制器 → 有界命令通道
                                  ↓
                              后台工作线程
                                  ↓

                                  ↓
Slint 属性 ← 控制器 ← 50 ms 事件轮询 ← 结果通道
```

**Core：** 公开操作使用 Rust 的输入/输出类型，完全不知道窗口的存在。工具目录为每个工具提供稳定的枚举 ID 和字符串路由；导航不依赖菜单下标。引擎是 `tools/` 内的适配器，因此未来的 CLI 或测试都能复用。每个工具暴露自己的稳定错误分类枚举（`DocumentIssue`、`JsonIssue`、`CryptoIssue`、`DiffIssue`、`CodesIssue`、`ClipboardIssue`、`CleanupIssue`、`ImageIssue`），桌面层不需要去匹配错误字符串。几何位置以归一化比例而不是像素离开核心层，条码的位置因此在缩放过的预览上依然成立。「什么可以被删除」的规则也放在核心层，紧挨着产生这份列表的扫描，而不是放在展示它的页面里。

**桌面控制器：** `controllers/mod.rs` 是外壳。它把目录条目翻译成 Slint 模型，按工具名或引擎做大小写不敏感的导航过滤，持有语言与唯一的提示通道，并把工作线程事件分发给对应的工具。工具控制器持有自己的状态、注册自己的回调、在切换语言时重绘自己的文案；它只通过 `submit`、`dispatch`、`finish`、`notify` 与外壳打交道。使用弱组件句柄避免 UI 所有权循环。只有主线程会碰 Slint 属性。所有控制器作为一个 `Tools` 值一起传递，于是路由拖入的文件、切换语言后重绘、分发事件这三件事各多一个字段，而不是给三个签名各多一个参数。拖入的文件先看当前页面——对任何文件都收的工具（哈希与加密、文本对比）优先；再看扩展名归属（`.age`、图片、`.json`）；都不匹配则交给文档转换。

**工作线程：** 一个命名线程处理有界通道，UI 侧以非阻塞方式提交。文件选择器、解析、剪贴板访问和导出都在这里执行，按工具分在 `worker/` 下，剪贴板上下文在它们之间共享。只有「监听剪贴板」做不到这一点：它会一直阻塞到被停止，所以它有自己的线程，发现变化后通过同一个命令通道报回来——而且绝不在通道里阻塞，因为按钮点击要用同一个位置——随后的读取像别的任务一样在工作线程上执行。那个线程只在开关打开期间存在，丢掉它的句柄就结束了。命令拥有自己的输入，事件拥有自己的结果。可恢复错误和解析器 panic 都会清除忙碌状态。`submit` 为用户操作占用忙碌状态，并拒绝第二个操作；`dispatch` 用于后台工作，例如工作台的校验——它不会阻塞界面，只是等一个空闲的轮次。事件定时器在整个窗口生命周期内由应用持有。没有任何服务器或网络服务。

**新增工具：** 在目录里把它标为 `available`，然后加上 `tools/` 下的模块、`worker/` 下的命令/事件模块、`controllers/` 下的控制器、`ui/state/` 下的状态全局和 `ui/pages/` 下的页面。外壳负责路由，其他地方都不用改。

操作结果以 `Toast` 呈现：窗口底部的浮动提示，到时自动消失。它是布局的兄弟节点而不是布局里的一行，因此出现和隐藏都不会引起页面重排，也不会占用结果面板的高度。它也从不被创建或销毁，所以淡入淡出都能播完；新的提示到来时会重置倒计时而不是沿用剩余时间。错误比成功提示停留更久，点击可以立即关闭。`StatusBar` 刻意做成静态的：它被所有工具共用，放在那里的临时消息就必须在切换导航时清理。

**UI 组合：** 页面绑定到本工具的状态全局并发出它的回调；它们不做文件 I/O，也不引用引擎 API。外壳级别的属性（`busy`、`dragging`）仍然从 `app.slint` 往下传，`app.slint` 只负责组合外壳和路由。每个工具一个全局，把窗口本身的接口维持在所有工具共用的那部分，而不是每多一个字段就多一个属性。`Sidebar` 组合 `NavItem` 和 `TextField`；`DocumentsPage` 组合 `PageHeader`、`FileCard`、格式 `Badge` 和 `SourcePanel`；`JsonPage` 组合 `PageHeader`、`TextField`、`JsonInput`、同一个 `SourcePanel`，以及自己的一行校验结果（含 `Toggle`）；`SourcePanel` 组合 `Action`、`CodeView` 和 `EmptyState`，`JsonInput` 组合 `TextEditor`；`DiffPage` 组合 `PageHeader`、两个 `Toggle`、一个 `Action`、两个 `DiffInput` 和一个 `DiffPanel`——差异面板自成一个结果卡片，因为差异的一行是行号槽、标记和正文，而不是一个字符串。`ImagesPage` 组合 `PageHeader`、同一个 `FileCard`、一个 `ImageList`，右侧则是上下叠放的 `PicturePanel` 与 `DetailList`；输出设置与两个按钮都是页面里的行：生成报出的体积，必须和产生它的那些控件挨在一起。它的行携带两种选中状态——勾选与显示——因为「批量会写出哪些」和「页面正在展示哪一张」是两个问题。`CleanupPage` 组合 `PageHeader`、一个 `Segmented`、同一个 `FileCard` 和一个 `CleanupList`，确认条是页面里的一行而不是弹窗：那句话和执行它的按钮，就在勾选发生的地方。`ClipboardPage` 组合 `PageHeader`、自己的一张读取卡片（含一个 `Toggle` 和两个 `Action`）、一个 `ClipList` 和一个 `ClipDetail`；详情卡片通过 `family` 属性复用 `CodeView`，因为剪贴板里的内容是别人自己写的话的概率，和是一条路径一样高，而它的导出按钮只对图片出现。列表行的单行预览用裁切而不是 elide：elide 会退到最后一个词边界，而中文句子没有词边界，于是一行中文只会剩下第一个空格之前的部分。`CodesPage` 组合 `PageHeader`、同一个 `FileCard`、一个 `CodePreview` 和一个 `SymbolList`：预览把舞台按图片自身的宽高比定尺寸，于是图片的比例就等于舞台的比例；每个标记按中心点摆放并带最小尺寸，因为一维码是以一条线而不是一个框定位的。当前高亮的是哪个码属于视图状态，放在状态全局里，点击某一行或某个标记时两张卡片指向同一个码，不必绕一趟 Rust。工作台的两张卡片、以及文本对比的两侧，都各自放在一个普通 `Rectangle` 里并按它定尺寸：布局是按子元素的首选宽度分配空间的，装着一句话的卡片会不断挤占邻居。校验结果之所以是页面的一行而不是卡片的一部分，也是同一个原因。`CodeView` 和 `DiffPanel` 都把行放进 `ListView`：`for` 的直接父元素是 `ListView` 时会被编译成虚拟化的 repeater，这是大文档不卡的唯一原因——用一个 `Text` 装整篇时，一份 26000 字的中文文档会让窗口冻住十几秒，因为 FemtoVG 要整形全文才能测量尺寸，而它 1000 条的整形缓存在没有词边界的文本上会持续颠簸。`TextEditor` 是例外：编辑需要一个光标和一段选区，所以工作台的输入、以及对比的每一侧都是单个 `TextInput`，JSON 的 4 MiB 和每侧 2 MiB 上限正是让这件事可以承受的前提。`StatusBar` 在各工具间共享。视觉改动应放在最小的相关组件里，共享样式令牌放在 `Theme` 中。

工作区刻意采用小而类型化的命令/事件桥接，而不是动态插件 ABI 或通用 JSON 分发：新增工具添加的是编译器会检查的枚举分支，而不是一个只能信任的注册表。

### 品牌与图标

品牌图形以两份做好的图标形式随仓库提供。主题中的藏青强调色与柔和米色背景取自它们的配色。

| 文件 | 画布 | 图形占比 | 使用方 |
| --- | --- | --- | --- |
| `assets/app-icon.png` | 256px | 铺满画布 | 侧边栏 `Brand`、Slint 窗口图标 |
| `assets/macos-icon.png` | 512px | 80.5%，四周透明留白 | 运行时 Dock 图标、打包的 `AppIcon.icns` |

两者都按 macOS 应用图标惯用的 22.37% 半径做了圆角。macOS 那份还额外遵循 Apple 的图标网格——图形占 1024 中的 824，其余透明；没有这圈留白，Dock 里的图标会明显比相邻应用大一号。而侧边栏和窗口图标是自己控制显示尺寸的，同样的留白只会让标识变小，这就是要分成两份的原因。

两个画布都刻意做得很小，因为它们会被编译进可执行文件：256px 足够 2 倍屏下 46pt 的侧边栏标识和窗口图标，512px 足够最大的 Dock 图标。尺寸每翻一倍，嵌入的字节数大约变成四倍——之前用 1024px 时，仅这两个图标就给每个平台的二进制增加了 1.7 MB。更换图形时需要自行准备这两个尺寸的文件。

`Brand` 负责侧边栏标识。`Icon` 负责展示并着色内置 SVG，`ToolIcon` 在桌面层把稳定的工具路由映射到图标。`Action` 接受可选图片，同时保留文字标签与键盘/无障碍行为。`TextField`、状态指示器、文件操作和占位页都复用这些组件。这些 SVG 是项目原创资源，统一使用 24 × 24 视图框、1.7px 圆角描边，不依赖外部字体或网络请求。唯一的例外是 `github.svg`——它是 GitHub 自己的标识，按其品牌规范收录，仅用于标注指向本仓库的链接；它是实心剪影，不是描边图形。较大的文档空状态有自己的 SVG 插画。

`Theme` 的调色板只有浅色一套。在 macOS 的深色模式下，这会让近乎全黑的标题栏压在浅色窗口上方，因此 `macos.rs` 把应用外观固定为 Aqua，并把窗口主题设为浅色。后者无法用 Slint 自带的 `set_color_scheme` 完成：它的 winit 后端在 Apple 平台会把设置主题那段代码 cfg 掉（`use_winit_theme`），把窗口装饰留给系统跟随。设置时窗口必须已经存在，所以 `main` 先 show 组件，设置标题栏，再运行事件循环。

新增图标的步骤：把 SVG 放进 `ui/assets/icons/`，在 `ui/icons.slint` 中注册，然后使用 `Icon` 或 `Action.icon` 属性。新增菜单项时，在 `ToolIcon` 里补上工具路由映射。图标资源和视觉映射不要放进核心库。两种渲染器使用同一套内嵌资源。

### 本地化

`SettingsMenu` 是一个可复用的侧边栏组件：文字标识旁的齿轮按钮，点击弹出 `PopupWindow` 列出两种语言。整行并列的语言按钮，为一个很少改动的设置占掉了一整行侧边栏高度。两个选项保持各自的母语写法（`English`、`中文`），无论当前是哪种语言都认得出来。`ui/i18n.slint` 集中管理静态组件文案，通过响应式绑定跟随 `I18n.chinese`。Rust 侧的 `locale.rs` 负责翻译后的工具目录元数据、状态消息和应用错误描述。核心层的错误暴露为稳定的 `DocumentIssue`、`JsonIssue`、`CryptoIssue`、`DiffIssue`、`CodesIssue`、`ClipboardIssue`、`CleanupIssue` 和 `ImageIssue` 分类；翻译从不依赖匹配英文错误字符串。分类本身可以带数据——JSON 语法错误带着行号和列号——因此位置信息在切换语言后依然存在。工作线程事件携带类型化的消息/结果，在展示时才按当前语言翻译——包括在转换过程中切换语言的情况。文件路径、引擎名称和文档内容永远不翻译。

界面的比例字体跟随所选语言（`Language::font_family`）：中文用 PingFang SC、Microsoft YaHei 或 Noto Sans CJK SC，英文沿用原来的拉丁字体。这不只是排版问题，更是性能要求。当主字体缺少哪怕一个字形时，FemtoVG 渲染器就会为该文本元素重新查询系统回退字体列表——每次布局、每一帧都查一次，在 macOS 上实测约 0.6 ms/元素，另外还有一次性的 CJK 字体加载和字形光栅化开销。因此界面文案必须落在所属字体的覆盖范围内；英文徽标写作 `DOCUMENT TO MARKDOWN`，正是为了避开 Helvetica Neue 没有的 `→`。

原生文件对话框的标题和筛选器名称在打开时使用所选语言；原生按钮和系统对话框仍跟随操作系统语言。底层的系统/解析器诊断信息保留原文，放在翻译后的 **技术详情** 标签下。启动阶段的技术诊断和命令行帮助保持英文。

语言代码（`en` 或 `zh-CN`）会原子地写入平台配置目录下的 `language` 文件（`directories::ProjectDirs`）：macOS 为 `~/Library/Application Support/dev.handybox.HandyBox/`，Windows 为 `%APPDATA%\\handybox\\HandyBox\\config\\`，Linux 为 `$XDG_CONFIG_HOME/handybox/` 或 `~/.config/handybox/`。缺失或无效的设置默认回到英文。该目录不存放任何文档内容。保存失败时，所选语言在当前会话仍然生效，状态栏会提示无法记住这一偏好。

新增工具时，请在 `tool_text` 中补上两种语言的翻译；新增静态界面文案时，在 `ui/i18n.slint` 中加一个属性。用等宽字体展示的文案——jq 表达式及其占位提示——保持 ASCII，因为等宽字体没有 CJK 覆盖。新的运行时消息应作为类型化的 `Message` / `FailureKind` 变体加入，并同时提供两种语言。不要把翻译后的文本塞进工作线程事件，也不要为了切换语言重建窗口。

## 新增一个工具

1. 在 `handybox-core/src/catalog.rs` 中添加稳定的 `ToolId` 和 `ToolDescriptor`（或直接用已有的占位项）。定义名称、描述、引擎、计划中的能力与可用性。新增的「不可用」条目会自动获得导航入口和占位页面。
2. 添加 `tools/<tool>.rs`，定义类型化的输入、输出和公开操作。核心库里不要出现 Slint 和原生对话框。只有在实现真正用到时才添加引擎依赖。
3. 添加 `worker/<tool>.rs`，定义该工具的命令与事件类型和 `execute` 入口。保持队列准入有界；昂贵的工作不能在 UI 回调里执行。凡是可能跑飞的维度——输出条数、时间、输入大小——都要设上限，并把触顶情况写进结果，而不是一直挂着。为扫描和批量操作有意识地加上进度与取消能力。
4. 添加 `controllers/<tool>.rs` 来绑定回调并保留工具状态，并在外壳的事件轮询里注册它。始终对照工具目录校验路由。工具状态必须能在页面切换后保留。
5. 创建 `ui/state/<tool>.slint` 存放该工具的属性与回调、`ui/pages/<tool>.slint` 存放布局，复用共享组件，并在 `ui/app.slint` 中添加路由。页面特有的布局留在该页面内。只有 UI 需要展示的数据才扩展 `ui/types.slint`。
6. 测试真实的输入/输出与失败行为。对于破坏性工具，必须先给出具体的结果预览并要求显式操作，才能修改文件。对压缩包要校验解压路径和展开后的大小。剪贴板监听必须是可选开启的。
7. 把目录条目标记为可用，必要时更新工作区的工具数量，并更新本 README 的状态表。可用的条目必须有能正常工作的页面和控制器。

## 渲染

渲染器配置具备回退能力，并对照 Slint 1.13.1 的后端源码做了验证。**FemtoVG/OpenGL** 和**软件**两种渲染器都会被编译。Winit 优先选择 FemtoVG；如果窗口/绘图表面创建时无法初始化它，后端会尝试软件渲染器。把回退放在窗口创建这一步很关键：只在后端选择阶段捕获错误为时过早。

`SLINT_BACKEND=winit-software` 请求 CPU 渲染，`SLINT_BACKEND=winit-femtovg` 请求 GPU 渲染，两者都走相同的后端回退机制。设为 `winit` 或不设置则使用默认值。不支持的后端名称会在启动时报错。直接依赖的 `i-slint-backend-winit` 与 Slint 版本耦合，必须和 `slint-build` 一起升级。

界面使用基础的矩形、边框和文本，而不是依赖 GPU-only 渲染的特效。启动时的自动回退无法挽救所有会话中途的驱动故障。在目标机器上应同时验证 GPU 与强制 CPU 两种会话。

参考：[Slint 渲染器](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/)、[锁定版本的 Winit 后端](https://docs.rs/i-slint-backend-winit/1.13.1/i_slint_backend_winit/)、[anydoc API](https://docs.rs/anydoc/0.2.4/anydoc/)。

集成测试覆盖了 CSV 的 Unicode/表格输出、按内容检测的 RTF、真实的 DOCX ZIP 容器、无效/空/缺失/超大输入、完整结果导出、源文件覆盖保护、Unix 上的符号链接保护、确认后的目标覆盖、Unicode 安全的预览截断以及工具目录一致性。JSON 部分覆盖了格式化与压缩、使用标准库的 jq 表达式、超大整数、JSON 流、语法错误位置、三类错误、输出上限、`halt`、文档概要与导出安全。文本对比部分覆盖了各侧的行号、完全一致与换行符、忽略空白后的匹配、只看变更时的上下文与省略行、含空区间的 unified 输出、行数与体积上限、文件读取与导出安全。条码部分自己画码再读回来，覆盖了带非 ASCII 内容的二维码及其位置、同一张图上多种码的阅读顺序、浅色印在深色上的码、什么都没有的图片、缩放后的预览与不变的位置、扩展名归属，以及文件、格式和像素上限。剪贴板部分覆盖了同一份内容再次到来、按条数与按字节的淘汰、永远留下的那一条、移除后归还的空间、展示用大小与实际占用内存的区别、空内容与超大内容的拒绝、文本/文件/图片的单行摘要、从 URI 解码文件引用（包括 Windows 盘符和并非转义的百分号），以及导出图片：写出的确实是收下的那些字节、扩展名不对时不留下任何文件、以及覆盖已有文件。磁盘清理部分会先造出文件夹再读回来，覆盖了跨文件名与目录、按内容找到的重复，大小相同但内容不同的文件，开头一致而结尾不同的长文件，被跳过的版本库目录，只在最上层报告的空目录树，按体积排序的大文件，以及横在「勾选」与「回收站」之间的那些规则——什么都没选、某组全选、扫描后发生变化或已消失的文件、不在该文件夹内的路径、不再为空的目录，以及出现在原文件位置上的符号链接。这些测试从不调用 `remove`：那会把文件真的丢进运行测试者的回收站。图像处理部分会列出一个文件夹并检查只有其中的图片被列出、按名称排序且不进入子文件夹，检查批量导出按各自的文件名写出、并拒绝已存在的同名文件与原图本身，还会把同一张图写成这个版本支持的每一种格式再读回来，检查缩放是否保持比例、宽度为零是否被拒绝、优化器是否从不增大体积也从不改动像素、JPEG 的质量是否真的对应体积，以及导出是否会拒绝错误的扩展名和原图本身。
